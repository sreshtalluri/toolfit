## Problem Statement

Tool descriptions are the entire API surface an agent sees, and they're written last, in a hurry, with no feedback signal when they're wrong. Research across 10,831 MCP servers found description quality moves tool-selection accuracy by roughly 9-12 points, more when similar tools compete. At least six tools already grade this (mcpgrade, mcpx, MCProbe, lastmile-ai/mcp-eval, MCPJam Inspector, academic benchmarks) — every one of them stops at a number and a complaint. None proposes a specific fix, applies it, re-runs the eval, and proves the delta. That closed loop is the open ground.

toolfit: **finds the specific places an MCP server confuses models, and proves a fix with a before-and-after eval — not just proposes one (mcpgrade and MCProbe already suggest fixes; nobody re-runs the eval and shows the verified delta).** *(Narrowed from an earlier, broader "proposes a fix" claim after cross-model review — mcpgrade/MCProbe already advertise recommended fixes; the actual, defensible gap is the verified re-measured delta specifically.)*

## The Core Technique (inverted generation)

The credibility of the whole project rests on structurally reducing circular ground truth — if a model both invents the task and grades what "correct" means, the eval measures agreement with that model's opinion, not real correctness. toolfit inverts the order instead:

1. Pick one target tool, e.g. `create_event(title, start_time, attendees)`.
2. Sample a concrete, valid argument set directly from its JSON schema: `{title: "Sync with design", start_time: "2026-09-02T14:00", attendees: ["sam@co.com"]}`.
3. Ask a generator model to write the natural-language request a user would send that leads to *exactly those arguments* — without naming the tool: `"Set up a meeting called Sync with design at 2pm on Sept 2 with sam@co.com."`
4. Ground truth is the sampled tuple from step 2, not the generator's opinion. Grading is a structural comparison: did the model under test call the right tool with arguments matching the tuple.

**Residual circularity risk (flagged by cross-model review, not fully solved):** the generator model still sees the catalog's actual description wording when writing the task, so it can echo that phrasing — a second model validating the task doesn't remove this dependency. The ground truth *tuple* is independent of the generator's opinion, but the task *wording* isn't fully independent of the catalog's own text. Spike mitigation to test: does withholding tool description text from the generator's context (giving it only the JSON schema, not the prose) close the gap further? If yes, that becomes the default; if it meaningfully hurts task naturalness, keep description text visible and document the residual risk explicitly in the methodology section instead of claiming it away.

Mutation testing (Premise-level technique, used both for measurement and for `--fix`) applies this same structural grader twice — once against the unmodified server, once after perturbing or rewriting one description — and attributes the score delta to that specific text change.

## What Makes This Cool

The "whoa" isn't the grade — it's the receipt. Re-ranked after cross-model review: **the fix diff is the actual differentiator and leads; `scan` is the front door, not the pitch** — static zero-config grading is already commodity (mcpgrade/mcpx do it too), so leading marketing/README copy with it undersold the real gap.

1. **The fix diff, scoped honestly (the differentiator — leads the README/pitch).** `--fix` produces a protocol-level patch (tool description A → B) plus the measured score delta (e.g. 61% → 84%, the source doc's own worked example) — the proof, not just the complaint. This is the "why toolfit and not mcpgrade" claim, narrowed per the Problem Statement above to the verified re-measured delta specifically.
2. **The one-liner (the front door, not the differentiation claim).** `uvx toolfit scan <server>` → a fast, static-only, zero-model-call grade (catalog fetch + lint rules, M0-level) in well under a minute, zero config, zero install step. This is what got the user's own excited reaction in office-hours — its job is "get someone to try it in 10 seconds," not "prove we're different." `scan` and `eval` are separate subcommands per the source doc's own architecture (`cli.py`: `scan | eval | fix | report`) — the full model-graded report (schema sampling, live model trials, confidence intervals — M1+) is `toolfit eval <server>`, matching the source doc's separate "under ten minutes" goal. The two commands should never be conflated: `scan` is the fast/free path, `eval` is the slower/paid one.
3. **The tool confusion map** (added by the cross-model review, see below): a small annotated graph — nodes are tools, edges are the specific pairs models confuse, each edge labeled with cause and fix — is a sharper shareable visual than a matrix table. Screenshot-native, self-explanatory out of context.

Two growth mechanics worth building in from the start, surfaced this session but absent from the source product doc: a **locally-generated static SVG badge** (`toolfit: 61 → 84`, the same worked example as the fix diff above, produced by `eval`/`--fix` — never by the static `scan`), same model as Python's `coverage-badge` — the user runs `toolfit eval --badge` and commits the SVG themselves, no hosted badge service, consistent with the "no web UI" non-goal — and framing the mutation finding as a single tweetable sentence ("we changed one sentence and accuracy jumped 23 points") rather than burying it in a report. **Badge integrity requirement (cross-model review):** the badge must carry (embedded or linked) model versions, task-suite hash, n, and seed count — not just the bare number. Without visible benchmark identity, the badge incentivizes cherry-picked local evals, which would undermine the exact "verified deltas, not vibes" credibility mechanism the whole project is built around. Same spirit as Section 5's "every metric with n, seeds, and CI" requirement, applied to the badge specifically.

## Constraints

Non-goals (unchanged from source doc, re-confirmed this session):
- No web UI — CLI + markdown/JSON only.
- No multi-server orchestration — one server per run.
- No security or prompt-injection testing — adjacent, actively developed by other tools (confirmed by this session's landscape check), and a scope trap.
- Not a frontier-model leaderboard — that's MCP-Atlas's job, not this tool's.
- No researcher/pre-product persona to serve — primary user is the MCP server author running this in CI.

New constraint from this session: **the fix loop never reaches into a third party's source repository.** See Premises.

## Premises

1. **`fix.patch` is a protocol-level diff only.** Computed entirely from what `tools/list` returns on a live server — description text A → B — never source code, never requiring repo credentials. Turning a finding into an actual PR against someone else's repo stays a manual, human action using the harness's output as content. A `--repo .` flag that greps-and-replaces the matching string in your *own* checked-out server is a safe, legitimate add-on for a later milestone, not milestone-numbered yet (you own the repo, `git diff`/revert is your safety net) — a bot that clones arbitrary third-party repos and opens PRs is explicitly not in scope. *(Surfaced by the user's own pushback: "wouldn't that require access to their actual repo?")*
2. **Distribution is Python, via PyPI.** `uvx toolfit scan <server>` is the zero-install quickstart; `pipx install toolfit` for persistent/CI use. This was a real decision, not a default — npm was considered and rejected because the project's architecture (`cli.py` + typer) is already Python, the harness talks to target servers over the MCP protocol rather than importing their code (so the target server's language is irrelevant to this choice), and Python's ecosystem fits the statistics-heavy grading work (confidence intervals, seeds) better. `connect/` should wrap the official `mcp` Python SDK for transport rather than hand-rolling stdio/HTTP.
3. **The source doc's outreach playbook (Section 10) is explicitly out of repo scope.** It's the founder's personal GTM motion, not a repo feature. This design doc, and the repo it describes, serve a general-purpose open-source user — any MCP server author — not a target-account list.
4. **Milestone scoping (source doc Section 8, M0–M4) is confirmed correct as written.** Explicitly re-checked this session — nothing to cut. Precisely: M0–M3 is the 10-day public v0 ("loud finish," see Approach A); M4 (the fix loop) is a distinct following phase at days 11-16, not inside the 10-day figure — the two were conflated in an earlier draft of this doc. The scope confirmation is not a schedule guarantee: it's contingent on Premise 5's spike actually working within its bounded time. If the spike shows the core technique needs more iteration than a weekend, the schedule — not the scope — is what should give. **Checkpoint (cross-model review — the 10-day figure was independently challenged as tight by Codex, having already been confirmed once in office-hours):** if the spike + M0 + M1 aren't done by day 5, the M3 launch date slips explicitly — the schedule risk surfaces early and visibly rather than silently compressing scope on day 9.
5. **A spike comes before M0 — disposable *scope*, not disposable *code*.** Prove the core loop (inverted task generation → grade → mutate description → measure delta → propose fix → re-verify) end-to-end on one toy stdio server with ~3 tools, over a weekend, before writing any of the public-facing M0. This de-risks the most novel and least-proven part of the whole project (does inverted generation + mutation testing actually produce a clean, believable signal?) before 10 days are committed to the public build. *(Revised after cross-model review: originally called "throwaway code," but the spike necessarily builds the hardest reusable infrastructure — catalog interception, task generation, grading, report format — so if it works, that code is intended to graduate into M0/M1 rather than be rebuilt. What's disposable is the narrow scope (1 server, 3 tools, 1 model), not the code itself.)* Not part of the milestone numbering.
6. **Data handling: schemas and generated task prompts go to whichever model provider the user configures, using the user's own API key — toolfit itself never retains or forwards data elsewhere.** Dry-run mode (default) means the *target server* never receives a real call, but the *LLM provider* doing the grading does see the tool catalog and sampled task text. Worth a one-line disclosure in the README given some scanned servers may be internal/proprietary.
7. **API cost is bring-your-own-key for end users — "zero config" is not "zero cost."** A full graded `eval` run makes real calls to whichever providers are configured (the static `scan` remains free — no model calls). The M3 launch corpus (15 public servers × 3 model adapters, per source doc M2/M3) is a real, modest out-of-pocket cost the founder funds directly for the launch evidence — budget for it before M3, exact figure TBD once the spike shows real token counts per task.

## Engineering Requirements (from /plan-eng-review)

Added during the engineering review pass, before any code is written:

1. **Concurrent execution in `run/`.** (Architecture #1) `eval`'s "under ten minutes" promise (Distribution Plan) requires concurrent task execution across providers/seeds — the v2 `mcp` SDK's `Client` is already an async context manager, so this fits naturally. Serial execution risks silently breaking that promise once a catalog has more than a few tools.
2. **Retry/backoff on provider rate limits.** (Architecture #2) The M3 launch corpus (15 servers × 3 providers × seeds) is exactly the bursty call pattern that trips 429s. `run/` needs exponential backoff, not just raw calls — otherwise the launch-evidence run itself risks producing incomplete data on the day it matters most.
3. **API keys are env-var-only; every persisted artifact is scrubbed before writing, not just keys/tracebacks.** (Architecture #3, broadened per cross-model review) Never accept keys via CLI flag (leaks into shell history). `report/` strips exception text/tracebacks before writing `report.md`/`report.json` — but the scope is wider than credentials: `toolfit-replay.jsonl`, transcripts, generated tasks, sampled IDs, and schemas can all leak a scanned server's proprietary details even with zero keys present, which matters given Premise 6 already acknowledges scanned servers may be internal/proprietary. The rule: nothing persisted to disk reveals more than what's needed to explain the finding. The whole badge/report-sharing growth loop depends on people posting these publicly, so any leak here is a real incident, not a hypothetical.
4. **`safety/` is a dependency-free leaf module.** (Architecture #5) It's used by both `connect/` and `run/`, but never imports from them or anything else in the tree — the module the doc itself calls "a feature, not overhead" should be trivially auditable in isolation.
5. **`gen/` and `fix/` need an eval suite, not just unit tests, from the spike onward.** (Test Review #1) Both make LLM calls whose *output quality* is the actual risk (a generated task that names the tool, a rewrite that's technically different text but equally vague) — a plain unit test only catches "did it return a string." This is the code the whole circular-ground-truth argument (source doc Section 4) rests on.
6. **`safety/`'s model-classifier tiebreaker lives in `run/`, injected into `safety/` via a small interface — not imported directly.** (Cross-model review — this corrects a self-contradiction in Architecture #4/#5 above: the source doc's safety design uses a model classifier as a fallback, which requires calling a provider, but #5 also required `safety/` to be dependency-free.) Resolution: `run/` implements the classifier and passes it into `safety/` as a callback/interface at call time, so `safety/` never imports `run/` directly and stays auditable in isolation, while the classifier logic still exists.

## Approaches Considered

### Approach A: Quiet Start, Loud Finish
Repo stays public and committing in the open from day 0 (post-spike), but zero promotion until M3 ships with the mutation evidence to back the claim up. Effort M, risk low. Honest, inspectable git history by launch time; no coordination overhead mid-build. Risk: someone finding it early sees an undifferentiated static linter — the "reads as a clone" risk the source doc already flags as High severity.

### Approach B: Silent Build, Single Launch
Repo unlisted/draft through all of M0–M3; one polished launch carries everything at once (matches the source doc's M3 as literally written). Effort S, risk medium (all distribution risk concentrated in one shot, no early signal if the mutation methodology underdelivers).

### Approach C: Build-in-Public, Milestone-Gated
Public and actively promoted from day 0, with small honest posts at M0, M1, and the M3 launch. Effort L, risk medium-high — compounding attention and a chance for early feedback to reshape M1/M2, but the highest risk of triggering the "looks like a clone" reaction on day 2, and cuts against the source doc's own evidence-first voice.

## Recommended Approach

**A — Quiet Start, Loud Finish.** Closest fit to both the source doc's established voice (careful, evidence-first — "publishing a grade with no variance is how you get correctly torn apart") and this session's stated goal (open source/research, adoption and stars as the outcome, not fundraising). It doesn't gate the repo's mere existence — so the commit history is real and available for anyone who checks — but spends zero promotion capital before the differentiator (confusion matrix + mutation delta) actually exists to back the claim up.

## Failure Modes

Not covered by the source doc — surfaced during review, needs defined behavior before M1:

- **Unreachable or timed-out server:** report the connection failure explicitly in the output; never produce a partial grade that looks complete.
- **Malformed or missing schema on a tool:** flag that tool in the report and exclude it from scoring rather than crashing the whole run.
- **Auth-required server:** dry-run mode only needs `tools/list`; if even catalog fetch requires auth the harness doesn't have, report "auth required, could not fetch catalog" rather than failing silently.
- **A mutation or fix that makes the score worse:** report it explicitly, never suppress it — this is the same "show the rejected changes" ethos the source doc already applies to `--fix` (Section 7), extended to measurement in general.
- **Hallucinated or nonexistent tool call:** the model under test calls a tool name that isn't in the catalog at all — a common, well-documented LLM failure mode this tool exists specifically to study. Scored as a miss by `grade/`, never a crash, never silently dropped.
- **Fix-generation failure:** the rewriter returns an empty, identical, or clearly-unrelated description. Rejected before it's even re-measured — same spirit as the noise-threshold rejection already above.

## Open Questions

- **Does inverted generation + mutation testing actually produce a clean, low-noise signal in practice?** Still unresolved, but no longer unexamined — the spike was actually run against a real model (2026-08-27) and produced three concrete, diagnosable findings instead of a clean yes/no. Recorded here rather than lost, so M1 starts from evidence instead of repeating the same runs:
  1. **Task-phrasing confound on the create/update pair.** `update_task`'s proposed fix ("...rather than creating a new one") independently verified as resolving the catalog's ambiguity (a second-model solvability check — see below — found zero issues against the fixed catalog), yet the model-under-test still failed every trial. Root cause: the generated task text itself was phrased with "create"/"add" language regardless of which tool the sampled arguments targeted, fighting the fix's disambiguating wording. The task generator has no signal telling it to phrase update-shaped arguments (an existing ID + new field values) as "modify," not "create" — this is a task-generation gap, not a description-quality one, and it's specific to tool pairs where one operation modifies something the other creates.
  2. **`schema_sampler.py`'s example pool was too small to guarantee seed diversity — now fixed, and now honestly reported.** `_EXAMPLES["status"]` had only 2 values (`open`/`done`); running seeds `[1, 2, 3]` through `random.Random(seed).choice(...)` produced the *same* value three times, collapsing what was meant to be 3 independent trials into 1 trial run three times. Fixed two ways: the pool is now 3 values (`open`/`in_progress`/`done` — a real third status, not padding), and `schema_sampler.count_distinct()` + `run_spike.py`'s aggregate summary now report how many of N sampled trials were actually distinct, rather than silently presenting a collided trial as independent evidence. Even with the larger pool, an 8-seed run still only produced 3 distinct values (birthday-paradox math — this doesn't fully disappear with a bigger pool) — the honest reporting is the real fix, not the pool size.
  3. **The generator has a strong, description-independent prior toward "list"-flavored phrasing for `count_tasks`.** Tested `count_tasks`/`list_tasks` — a pair deliberately designed to avoid finding (1)'s confound, same argument shape, neutral shared description. Across 8 trials (3 distinct sampled values, per finding 2's fix), the generator wrote "show me..."/"can you show me..." for `count_tasks`'s arguments 100% of the time — a sentence that unambiguously describes *listing*, not *counting*. Both `Before passed` and `After passed` were 0/8: the description fix made no measurable difference, which makes sense once the task text itself never asked for a count in the first place. The model calling `list_tasks` in response isn't wrong given that text; the generator failed at its own core job (writing English that leads to exactly the sampled tool+arguments) for this schema shape, regardless of description quality.
  4. **Withholding the description entirely (`TOOLFIT_WITHHOLD_DESCRIPTION=1`) isolated whether finding 3 was the vague description's fault — it mostly wasn't.** For `status=open` (5/5 trials), the generator produced the *identical* "show me..." text with and without any description visible — a pure prior of the generator model itself, unrelated to `count_tasks`'s description text. For `status=done`/`in_progress` (3/3 trials), removing the description changed the failure mode rather than fixing it: the generator switched to *update*-flavored misreadings ("Mark this task as done" — reading the status value as an instruction to set, not a filter to apply), which the model then correctly declined to act on (no call, rather than a wrong call). So the vague description wasn't doing nothing for those values — it was steering away from an even worse misreading, just not toward the right one. Across all 16 trials in both runs, `count_tasks` was never correctly represented once. This looks like a real limit of inverted generation specifically for aggregate/count-style operations, which don't have as natural a user-facing "ask" as create/list/update do — worth a dedicated look during M1's task-generation hardening, not something a better description alone will fix.

  **What did get validated:** the Tier 1 "second model reviews for solvability" guardrail from the source doc (S4) was missing from the spike and has now been built (`gen/taskgen.py::check_solvability`, wired into `scripts/run_spike.py` against both the original and fixed catalog, tested offline via a fake client and against a real model). It correctly and independently flagged the create/update catalog as ambiguous using only the tool list — no argument info, no knowledge of the "right" answer — which is real evidence the guardrail mechanism itself works, even though the end-to-end before/after signal isn't clean yet. The `check_no_leakage` guardrail (tool-name-string check) remains a heuristic, not the model-based review the source doc originally specified for leakage too — worth revisiting during M1 if leakage-by-synonym (not just literal name) turns out to matter.

- Exact rendering of the tool confusion map (ASCII in markdown vs. a rendered image via graphviz/mermaid) — affects the M3 report tooling, not yet designed.
- Whether `mcp-test-harness` (found during this session's landscape check — protocol-level, deterministic, no LLM) is worth a closer look for reusable schema-validation utilities, or just a one-line mention in the README's landscape table.

## Success Criteria

Adapted from the source doc's Section 11. Split per cross-model review — the original list mixed outcomes the repo build actually controls with outcomes it can only enable, which is a real inconsistency against Premise 3 (outreach out of repo scope):

**Repo-controlled (the build is directly responsible for these):**
- The harness runs against at least fifteen public servers without hand-holding.
- The mutation result is reproducible by someone else from the README alone.

**Aspirational (the repo enables these but doesn't control them — not a build requirement):**
- At least one description fix, discovered by the tool, merged into a third-party server (by anyone, not necessarily the founder's own outreach).
- Stars are a lagging indicator, not a target — the source doc's own framing holds: one merged PR into a server people actually use beats two hundred stars. The badge and confusion-map artifacts (see "What Makes This Cool") are the mechanism for stars to follow from real usage, not a thing to optimize directly.

## Distribution Plan

- **Language/packaging:** Python, published to PyPI as `toolfit`.
- **Quickstart:** `uvx toolfit scan <server>` — zero install, static-only grade in well under a minute (matches the one-liner hook above). `uvx toolfit eval <server>` is the full model-graded report and is what the source doc's "under ten minutes, zero config" goal actually describes — the two commands have different time budgets and should be documented as such in the README, not blurred into one claim.
- **Persistent/CI use:** `pipx install toolfit`.
- **Transport base:** wrap the official `mcp` Python SDK rather than hand-rolling stdio/HTTP — it already exists and is maintained by the protocol owner.
- **CI integration:** GitHub Action (scoped in source doc M3, exact shape still an open question above).

## Pipeline (added during eng review)

```
scan (M0 — free, fast, no model calls)
  connect/ ──▶ lint/ ──▶ report/
     │
     └── safety/ (leaf module; dry-run interception, read-only classify)

eval (M1+ — paid, async, concurrent per Eng Req #1)
  connect/ ──▶ gen/ ──▶ run/ ──▶ grade/ ──▶ report/
                 │         │         │
                 │         │         └── tasks/ (cache, keyed by catalog hash)
                 │         └── safety/'s model-classifier tiebreaker,
                 │             injected from run/ (Eng Req #6) — safety/
                 │             itself never imports run/
                 └── negative-sampling: targeted near-neighbor tasks
                     between similar tool pairs, not just 1/tool (M1)

  mutation harness = grade/ run twice (before/after 1 description edit),
  paired trials + fixed seeds + named significance test (M2)

eval --fix (M4)
  [grade/'s mutation output] ──▶ fix/ (rewriter) ──▶ connect/ (protocol-level patch: description text A → B)
                                                        │
                                                        └──▶ grade/ (re-verify) ──▶ report/
                              NEVER touches a third-party source repo or requires repo credentials (Premise 1)
```

## Next Steps

1. **Spike (private, before anything public — disposable scope, not disposable code per Premise 5):** one toy stdio server, ~3 tools, one model. Prove: schema-sample → inverted task generation → run → structural grade → mutate one description → re-measure delta → propose fix → re-verify. Markdown output only. Skip HTTP, multi-model, CI. Code that works here is expected to graduate into M0/M1, not be rebuilt. **Also validates, per cross-model review:** (a) whether withholding description text from the generator's context reduces residual circularity (see The Core Technique); (b) an OpenRouter model's tool-call/JSON-strictness behavior, before M2 commits to it as a third adapter.
2. **M0 (days 1-2):** `connect/` wrapping the official `mcp` SDK, stdio + HTTP transports, catalog fetch, static lint rules. This layer is structural only — no model calls, no grading of behavior, just rules over the catalog text/schema itself (e.g. "this parameter has no description"). This is the fast path behind the one-liner. **Also starts, per cross-model review:** the audit of 15 candidate public servers for the M3 corpus — auth requirements, local env needs, side effects, OAuth, nontrivial launch commands — tracked as a dependency, not a day-9 open question.
3. **M1 (days 3-5):** schema sampler, inverted task generation + validator, structural grader, confusion matrix (and confusion map) in the report. This layer adds live model behavior on top of M0: it runs a model against generated tasks and grades its tool/argument choice against the sampled ground-truth tuple. First point where the tool actually measures a model, not just the catalog text. **Hardened per cross-model review, not deferred:** the schema sampler handles real JSON Schema complexity ($ref, oneOf/anyOf/allOf, formats, regex, nullable fields, defaults, dependent constraints) rather than only toy-server-simple schemas; the structural grader applies canonicalization (dates/timezones, array order, normalized emails, equivalent enum phrasing) so semantically-equal answers don't register as false failures; task generation includes deliberate negative-sampling (targeted near-neighbor tasks between similar tool pairs), not just one positive task per tool — without it, confusion-matrix off-diagonal mass risks being noise rather than signal.
4. **M2 (days 6-8):** three model adapters (Anthropic/OpenAI/OpenRouter — OpenRouter's compatibility already validated in the spike per above), seeds + confidence intervals, mutation harness. The mutation harness is not a fourth grading mechanism — it's the M1 structural grader run twice (before/after a description perturbation) with the delta attributed to that specific text change. This produces the first real before/after finding. **Defined per cross-model review, not left as "confidence intervals" hand-waving:** the acceptance rule is paired trials on identical task suites with fixed seeds, a named significance test (paired bootstrap), and a correction for testing multiple mutations/descriptions at once — this is what actually prevents `--fix` from cherry-picking a good-looking run.
5. **M3 (days 9-10) — the "loud finish":** README with a real example run, `uvx`/`pipx` install path live on PyPI, GitHub Action, badge support, `eval` run across the audited 15-server corpus (from M0) published with mutation evidence. This is the first active promotion per Approach A, and closes the 10-day figure from Premise 4. **Designed per cross-model review, not a launch-day add-on:** the GitHub Action's cache layout, secrets handling, exit codes, artifact output, and cost/budget semantics are specified before M3 starts, since they depend on `report/`'s final shape from M1 and determine real CI behavior for anyone who adopts it.
6. **M4 (days 11-16, separate phase — not inside the 10-day figure):** the fix loop — rewriter, protocol-level patch emitter, A/B re-verifier, scoped per Premise 1.
7. **M5 (optional):** multi-turn workflows, failure injection — gated on traction, per source doc.

## M1 Design (added during M1 planning, 2026-08-27)

Detailed design for M1's four components plus the CLI surface that makes them usable, worked out after the spike (see Open Questions above) rather than in the abstract — today's findings directly shaped the task-generation section below.

**Scope boundary, restated because it's easy to blur:** M1 is measurement-only — one clean confusion matrix from one real run against one model. Mutation testing (`grade/mutator.py`) and the fix loop (`fix/fixer.py`) are M2 and M4 respectively, per the Next Steps list above — M1 does not wire them into the CLI. They stay exactly as the spike left them, available for M2 to pick up.

**1. Schema sampler hardening.** Extends `sample_arguments` beyond flat strings to: `integer`/`number`/`boolean`/`array`-of-primitives, `enum` (any base type), `format` (date, email, uuid), `nullable` fields (sampled both ways across seeds, deterministically), and simple `oneOf`/`anyOf` (pick one branch, seeded, recurse). Still raises loudly on anything unsupported (`$ref`, `allOf`, dependent constraints, regex-pattern generation) — same "fail loud, never silently sample wrong" rule the spike already established. `examples/toy_server.py` gains 1-2 tools with this real complexity so the hardening is actually exercised end-to-end, not just unit-tested against synthetic schema dicts.

**2. Task-generation hardening — source fix and detection layer, not one or the other.** Source fix: enrich the generator prompt with few-shot guidance for the shape found today — arguments that look like they reference an *existing* item (an id-like field alongside other fields being changed) get nudged toward "modify" phrasing over "create." This is a heuristic improvement, not a guarantee: the "count vs. list" bias found today has no clean structural signal to hang guidance on, since the generator only ever sees the description plus sampled arguments, and MCP tools carry no reliable output-shape signal to lean on instead.

*Deliberate deviation from the literal Next Steps wording above, recorded here:* "targeted near-neighbor tasks between similar tool pairs" implies a similarity-detection mechanism. Since the confusion matrix (below) already grades all pairs rather than targeting near-neighbors, the consistent, simpler choice is to generate **multiple tasks per tool** (not one) and grade every task against the *whole* catalog — genuine tool confusion surfaces in the matrix without needing to have pre-detected which pairs are similar. Near-neighbor-*targeted* generation (spending extra samples specifically on suspected-similar pairs) is a real optimization, deferred to M2+ once all-pairs grading shows it's needed.

Detection layer: `check_solvability` and `check_no_leakage` graduate from the spike mostly as-is, now run against the whole catalog per task (already how `check_solvability` works) rather than against one target tool.

**3. Structural grader canonicalization.** Before comparing arguments: normalize dates/timestamps to a common representation, compare arrays as multisets (order-independent) unless a schema marks order as meaningful, and case/whitespace-fold strings for enum and email comparison. Explicitly not doing semantic synonym matching (e.g. "urgent" ≈ "high") — that needs an LLM judge, which would contradict the project's core credibility argument (structural comparison against sampled ground truth, never an opinion). "Equivalent enum phrasing" means formatting equivalence here, not meaning equivalence.

**4. Confusion matrix.** For each tool, N generated tasks (per #2) run against the model-under-test, graded structurally, tallied into an intended-tool × actual-tool-called matrix (plus columns for "no call" and "hallucinated"). Rendered as a markdown table for M1 — fancier rendering (a graphviz/mermaid "confusion map") is already flagged above as an undecided M3 report-tooling question, not something M1 needs to resolve.

**CLI.** `src/toolfit/cli.py`, typer, one command for now: `toolfit eval <server_path> [--seeds N] [--model MODEL]`. `--seeds` defaults to 5 (5 tasks per tool) — enough to get real matrix density on a small catalog without a long-running default invocation; explicitly not a statistically-justified number (that's M2's paired-trial/CI work), just a reasonable default a user can override. Launches the server, builds the catalog, runs the full matrix, prints the report. No `--target-tool` flag — testing the whole catalog is the point of a confusion matrix, unlike the spike's single-target-tool `run_spike.py`.

## M2 Design (added during M2 planning, 2026-08-28)

**Goal:** three real model adapters, per-tool confidence intervals, and mutation testing wired into the CLI with a statistically defensible acceptance rule — turning M1's one-shot confusion matrix into a tool that can also test *whether a description fix actually helped*.

**Core data-flow change.** `build_confusion_matrix` already generates and grades a fixed set of tasks per tool; M1 threw the intermediate tasks/results away after tallying them into the matrix. M2 stops throwing them away: `ConfusionMatrix` gains `trials_by_tool: dict[str, list[TrialRecord]]`, where `TrialRecord(task: GeneratedTask, passed: bool)` is populated in the same atomic per-tool commit `build_confusion_matrix` already does (schema-warning tools still get no entry). This is what makes mutation testing a genuinely *paired* trial: it re-runs the exact same tasks (same seeds, same sampled arguments) against a patched description, rather than generating a fresh, non-comparable sample. "Before" results are read directly from `trials_by_tool` — no repeat API calls, and a guarantee that "before" in the mutation report is identical to what the base confusion matrix already measured.

**1. `grade/significance.py` (new).** Pure, offline-testable functions, no model calls:
- `wilson_interval(successes: int, n: int, confidence: float = 0.95) -> tuple[float, float]` — closed-form CI for a pass rate. Used for both the base eval report's per-tool rates and mutation's before/after rates.
- `paired_bootstrap_pvalue(before: list[bool], after: list[bool], *, resamples: int = 10000, seed: int = 0) -> float` — one-sided test of whether "after" improves on "before," resampling the paired delta.
- `bonferroni_correct(p_values: list[float], alpha: float = 0.05) -> list[bool]` — per-test significance after correcting for however many mutations were tested in one run (`--mutate` is repeatable).

**2. Third model adapter (`run/adapters.py`).** Add `OpenAIAdapter`. Refactor it and `OpenRouterAdapter` to share one `_openai_compatible_call()` helper — both are OpenAI-SDK function-calling, differing only in `base_url`/API key, so this removes duplication rather than adding it. `OpenRouterAdapter`'s docstring is promoted from "compatibility-check-only" (a leftover from the spike's Next Steps #1 validation) to a real third adapter — this is the M2 milestone the spike's TODO explicitly deferred to. Add `infer_provider(model: str) -> Literal["anthropic", "openai", "openrouter"]`: `"/"` in the name → openrouter (OpenRouter's own `vendor/model` convention), `claude*` → anthropic, `gpt*`/`o1*`/`o3*`/`o4*` → openai, else → anthropic (matches the current default). Add `build_adapter(model: str) -> ModelAdapter`, which also constructs the right client from env vars: `OPENAI_API_KEY` (read implicitly by `openai.OpenAI()`, same as `ANTHROPIC_API_KEY`/`anthropic.Anthropic()`) and `OPENROUTER_API_KEY` (explicit — same env var name `scripts/openrouter_check.py` and `.env.example` already use). A missing key raises before any network call, giving the CLI a clean error path to catch (matching the existing unreachable-server pattern) instead of a raw SDK traceback.

**3. Mutation trials (`grade/mutator.py`).** Add `run_mutation_trials(matrix: ConfusionMatrix, catalog: ToolCatalog, adapter: ModelAdapter, *, tool_name: str, new_description: str) -> MutationTrialResult`. Pulls `matrix.trials_by_tool[tool_name]` for "before," patches the catalog (reusing `patch_description`), re-runs only "after" for each of those same tasks, and calls `significance.py` for the CI/p-value. `MutationTrialResult` holds `tool_name`, `new_description`, `before_passes: list[bool]`, `after_passes: list[bool]`, `p_value: float`, and `significant: bool` (set after the caller applies Bonferroni across all mutations tested in one run — this dataclass doesn't correct itself, since correction depends on how many other mutations ran alongside it). The existing single-task `run_mutation_test`/`MutationResult` are untouched — still used by the spike/e2e test, not replaced.

**4. CLI (`cli.py`).** Repeatable `--mutate "tool_name:new description"` option on `eval` (split on the first `:`; an unknown tool name fails clearly, before any calls are made, same pattern as the existing unreachable-server error). `--model` alone selects the provider via `infer_provider`/`build_adapter` — no separate `--provider` flag, so `--model` stays the single source of truth. All `--mutate` p-values from one invocation go through one shared `bonferroni_correct` call.

**5. Report (`report/render.py`).** `render_confusion_matrix` gains a `## Pass Rates` section (per-tool rate + Wilson CI, using `trials_by_tool`). New `render_mutation_results(results: list[MutationTrialResult])` appended to the report when `--mutate` was used: before/after rate, CI, delta, p-value, and the Bonferroni-corrected significance verdict per mutation.

**Explicitly out of scope for M2** (confirmed against the Pipeline diagram above): the fix loop itself (`fix/fixer.py` wiring, protocol-level patch emission) stays M4 — M2 lets you hand-supply a candidate description via `--mutate` and get a rigorous verdict on it, but does not generate that candidate. Concurrency/retry (Engineering Requirements #1/#2) remain out of scope; `build_confusion_matrix` and the new mutation trials stay sequential, same as M1.

**Testing.** `significance.py` is pure math — full offline TDD coverage, no API key needed (known-answer cases: identical before/after → p≈1.0; all-fail-to-all-pass → p≈0; `wilson_interval` against textbook values for small n). `OpenAIAdapter`/`build_adapter`/`infer_provider` get an eval-style test file skipped without `OPENAI_API_KEY`, matching the existing skip pattern (`test_taskgen_eval.py`, `test_e2e_spike.py`). Mutation trial wiring gets an offline test using a fake adapter (`SimpleNamespace`, same style as `test_taskgen.py`), plus one real e2e case gated on API keys reusing `examples/toy_server.py`'s existing `create_task`/`update_task` ambiguity as the mutation target.

**Known limitation, flagged during M2's final review, not fixed in M2 (2026-08-28):** `paired_bootstrap_pvalue` is anti-conservative at small `n` — whenever every paired trial improves (no counter-evidence at all in the sample), the resampled delta is positive in every replicate, so `p` is exactly `0.0` regardless of how few trials were run. A single-seed mutation test where the one trial improves will report `p=0.0` and, after Bonferroni correction, SIGNIFICANT — on one data point. This is a property of the bootstrap-on-a-sample-with-no-counter-evidence approach specified above, not an implementation bug: the code faithfully implements what this section specifies. Options for a future milestone: floor the reported p-value away from an absolute 0 (e.g. at `1/resamples`), require a minimum number of discordant pairs before emitting a verdict at all, or switch to an exact test (e.g. McNemar's) for small `n`. Until addressed, treat any mutation verdict computed from a small `--seeds` value with real caution — the CLI does not currently warn about this.

## M0 Design (added retroactively during M3 planning, 2026-08-28)

**Context: M0 was skipped.** The project went straight from the private spike into M1 (`eval`); the codebase has no `scan` subcommand, no static lint rules, and no 15-server corpus audit. M3's "loud finish" (README with a real example, GitHub Action, 15-server corpus publish) depends on `scan` existing as the free, zero-model-call front door and on the corpus audit `scan` will help perform — so M0 is being built now, retroactively, sequenced immediately before M3's launch infrastructure.

**Goal:** a free, zero-model-call `toolfit scan <server_path>` command that catches the exact class of bug this whole project exists to find (duplicate/missing/thin tool descriptions) via pure static analysis — no API key required, runs in well under a second.

**Scope decisions (made during M0 planning):**
- **HTTP transport deferred.** The source doc's original M0 spec calls for stdio + remote HTTP transport; every server touched so far (toy server, all M1/M2 tests) is stdio-only, and adding HTTP now would be new transport code with nothing real to test it against. Revisit if the M3 corpus audit turns up an HTTP-hosted public server that needs it.
- **Three lint rules, not a broader set.** Grounded directly in this project's own findings rather than a generic lint-rule catalog:
  1. **`missing_description`** — flags any tool whose description is `None` or whitespace-only.
  2. **`short_description`** — flags a non-empty description under ~15 characters. Skips tools already caught by `missing_description`, so nothing double-reports.
  3. **`duplicate_description`** — catalog-wide: groups tools by a case/whitespace-normalized description, flags every group of 2+ tools sharing one. This is a static echo of the actual bug `examples/toy_server.py` was built to demonstrate (`create_task`/`update_task` sharing "Add a new task.", `list_tasks`/`count_tasks` sharing "Get tasks by status.").
  A broader rule set (near-duplicate detection, missing-parameter mentions, generic-verb collisions) was considered and deferred — more surface area for false positives on a tool's very first, credibility-setting run.
- **No numeric/letter grade.** `scan` prints a findings list only ("3 findings across 5 tools"), not a "Grade: B" — matching the credibility-first stance already established for `eval` (no LLM judge, never imply more precision than the method supports). A static heuristic score would invite "compared to what?" in a way a plain findings count doesn't.

**Components:**
1. **`lint/` (new package).** `LintFinding` dataclass: `rule_id: str`, `tool_name: str | None` (`None` for catalog-wide findings like duplicates), `message: str`. `run_lint(catalog: ToolCatalog) -> list[LintFinding]` runs all three rules and aggregates their findings.
2. **`report/render.py`.** New `render_lint_report(catalog: ToolCatalog, findings: list[LintFinding]) -> str` — findings grouped by rule, one-line summary count, markdown output matching the existing report functions' style (lines list, joined at the end).
3. **`cli.py`.** New `scan` command: `toolfit scan <server_path>`. Reuses `fetch_catalog`/`server_params` and the exact same "Could not connect to server" error-handling pattern `eval` already has. Runs `run_lint`, prints `render_lint_report`. No model calls, no API key needed anywhere in this path. The existing `@app.callback()`'s docstring promises to be revisited once a second command exists ("that's the point Typer stops collapsing on its own") — this must be verified empirically via `CliRunner` once `scan` is added, not assumed, matching how this exact Typer quirk was originally handled in M1.

**Testing.** Offline unit tests per rule using hand-built `Tool`/`ToolCatalog` fixtures (no I/O, no model calls). CLI smoke tests mirroring `test_cli.py`'s existing `eval` coverage (`--help`, missing argument, unreachable-server error). One real, **ungated** integration test running `scan` against `examples/toy_server.py` — since `scan` makes no model calls, this needs no API key and can run in every test invocation, directly proving `scan` flags the toy server's two real duplicate-description pairs.

**Explicitly out of scope for M0:** HTTP transport (deferred, see above), the 15-server corpus audit itself (a research/curation task using `scan` once it exists, not a code deliverable — tracked as an M3 prerequisite), any static rule requiring model calls or semantic judgment (stays in `eval`'s structural grading, never blurred into `scan`'s free/fast path).

## M3a Design (added during M3 planning, 2026-08-28)

**Context: M3 split in two.** M3 as originally scoped bundles genuinely independent pieces: buildable code (retry/backoff, badge generation, PyPI packaging, exit-code semantics) and launch mechanics that depend on research/curation and an operational publish step (the 15-server corpus audit, the GitHub Action, README, the actual launch-corpus eval run). M3a is the buildable-code half — SDD-cyclable the same way M0/M1/M2 were. M3b (the launch mechanics) is planned separately, after M3a, since the Action's design depends on M3a's exit-code decision and the corpus audit benefits from retry/backoff existing before hammering real servers at scale.

**Scope decisions (made during M3a planning):**
- **`--strict` is opt-in, not the default.** `scan`/`eval` both keep today's exit-0-always behavior unless `--strict` is passed — no behavior change for anything already built and tested in M0-M2. This is what lets the M3b GitHub Action opt into real CI gating without retroactively surprising existing users/scripts.
- **The badge doesn't require M4's `--fix` loop.** The source doc's badge example ("61 → 84") reads like a fix-loop before/after delta, but M2's `--mutate` already produces exactly that shape of data (`MutationTrialResult.before_passes`/`after_passes`). The badge works standalone (plain pass rate) or with a delta (when `--mutate` was also used) — fully buildable now, no dependency on unbuilt M4 work.
- **PyPI packaging stops at "verified buildable," not "published."** Completing metadata and verifying a clean-venv install is a code/config deliverable; the actual `twine upload` is a launch-day operational step that belongs with M3b's corpus run, not M3a's SDD cycle.

**Components:**
1. **Retry/backoff (`run/adapters.py`).** A single shared `_with_retry(fn, *, max_retries: int = 3, base_delay: float = 1.0, sleep_fn: Callable[[float], None] = time.sleep) -> T` helper wraps only the actual network call inside each adapter's `call_with_tools` (`client.messages.create` / `client.chat.completions.create`) — not the whole method, so parsing failures (M2's malformed-JSON handling) are never retried, only `anthropic.RateLimitError`/`openai.RateLimitError`. Exponential backoff with jitter (`base_delay * 2**attempt + random.uniform(0, base_delay)`), a stderr warning per retry, and a re-raise after `max_retries` is exhausted — never a silent swallow past the cap, matching the "fail loud" constraint carried over from M1/M2. `sleep_fn` is injectable so tests run instantly, the same dependency-injection pattern `grade/significance.py` already uses for its seeded `random.Random`.
2. **Badge (`report/badge.py`, new file).** SVG isn't markdown, so it gets its own file rather than growing `report/render.py`'s scope. `render_badge(matrix: ConfusionMatrix, mutation_result: MutationTrialResult | None = None) -> str` returns raw SVG text: `"toolfit: {rate}%"` standalone, or `"toolfit: {before}% → {after}%"` when a mutation result is supplied. Embeds model-under-test, generator model, seed count, and a short hash of the actual task suite (sorted `(tool_name, task.text)` pairs from `matrix.trials_by_tool`) as SVG metadata — satisfying the design doc's original badge-integrity requirement (Section "What Makes This Cool" above: no bare number without traceable benchmark identity). New `eval --badge` boolean flag writes to a fixed `toolfit-badge.svg` in the cwd — no custom output path in v0, kept simple.
3. **PyPI packaging (`pyproject.toml`).** Complete metadata: `readme`, `authors`, `classifiers` (Development Status, Intended Audience, License, Python versions), `urls.Repository`, `keywords`. Verify `uv build` produces a valid wheel/sdist, and verify a clean-venv install actually runs (`pip install dist/*.whl && toolfit --help`). No `twine upload` in this milestone.
4. **Exit codes (`cli.py`).** New `--strict` flag on both `scan` and `eval`. `scan --strict` exits 1 if `run_lint` returns any finding at all. `eval --strict` exits 1 if any tool's pass rate (from `matrix.trials_by_tool`) falls below `--strict-threshold` (default `0.9`) — a fixed, documented, CI-friendly rule, independent of whether `--mutate` was also used. Mutation-specific gating semantics (e.g. "fail if a candidate fix didn't significantly improve") are deliberately left to M4, which will need its own A/B-verification gating logic anyway.

**Testing.** Retry/backoff gets offline tests using a fake client that raises the rate-limit exception N times then succeeds (proving retry-then-success), and a fake that always raises (proving re-raise after `max_retries`, never silent) — both using an injected `sleep_fn` stub so tests run instantly, asserting the stub was called the expected number of times rather than actually sleeping. Badge gets offline tests on hand-built `ConfusionMatrix`/`MutationTrialResult` fixtures, asserting the SVG text contains the expected rate string and metadata fields. PyPI packaging verification is a manual/scripted check (`uv build` + clean-venv install), not a pytest test — there's no meaningful unit-test surface for "did the wheel build correctly" beyond actually building it. `--strict` gets CLI tests mirroring the existing `eval`/`scan` test style, covering both the pass-through-unchanged default and the new exit-1 paths.

**Explicitly out of scope for M3a:** the GitHub Action itself, the 15-server corpus audit, README, and the actual `twine upload`/launch-corpus run — all M3b, sequenced after M3a since they depend on its outputs (exit codes for the Action, retry/backoff before running the real corpus, a verified-buildable package before publishing it).

**`--strict` semantics when a tool couldn't be evaluated at all, clarified during M3a's final review (2026-08-28):** `eval --strict` only iterates `matrix.trials_by_tool`, so a tool excluded entirely by a schema warning (never sampled, never called) cannot be "below threshold" — it's simply absent from the check. If every tool in a catalog fails schema sampling, `--strict` exits 0: a green CI gate on a server that could not be evaluated at all. Rather than deciding unilaterally whether that should be a hard failure (a real policy question — M3b's Action design should weigh in), M3a's fix makes this visible instead of silent: `--strict` with any `schema_warnings` present prints an explicit stderr note naming which tools went unevaluated, alongside whatever pass/fail verdict the successfully-evaluated tools produced. Revisit whether this should escalate to a hard failure once the Action's own exit-code contract is designed in M3b.

## Post-M3a whole-branch review (2026-09-04)

**Significance test switched from paired bootstrap to exact McNemar (sign) test** — resolves the "Known limitation" recorded under M2 Design above. `grade/significance.py::paired_exact_pvalue` computes `P(X >= improvements | k discordant pairs, p=0.5)`; ties carry no weight, so 3 fail→pass with 2 ties reports `p=0.125` (correctly not significant at α=0.05) where the bootstrap resampled the ties and reported `p≈0.010`. Deterministic — no `resamples`/`seed`. Consequence for `--seeds`: with 5 seeds the smallest attainable p-value is `1/32 ≈ 0.031`, so a single-mutation run can only reach SIGNIFICANT if every trial flips fail→pass; with two `--mutate`s Bonferroni makes 5 seeds insufficient in principle. `--seeds 10` is the practical floor for mutation verdicts.

**Sampler now honours `required`** — optional properties are sampled with probability 0.5 per seed (seed still fully determines the draw). Previously every optional was always populated, so a 10-filter search tool produced a 10-argument task and the exact-match grader attributed any omission to description quality.

**Deferred, deliberately:** `--strict` still exits 0 when tools were excluded by schema warnings (policy owned by M3b Action design, see above); truncation/malformed-JSON no-calls are still tallied with genuine no-calls rather than in a separate `(error)` column — worth a column once the corpus run shows how frequent they are.
